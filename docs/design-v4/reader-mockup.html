B-Trees & Index Structures

JW Jonas Weber · Editor

Why binary trees fail on disk

✓ Cleared

A binary search tree is a beautiful structure for memory and a terrible one for disk. Every comparison follows a pointer, and on disk a pointer means a seek: for a million keys, a balanced binary tree performs around twenty of them. Twenty seeks per lookup is not a data structure — it is a queue at the hardware.

The insight behind every disk-based index is that a seek fetches an entire page, typically four to sixteen kilobytes, whether you use one byte of it or all of them. If you are paying for the whole page, the structure should fill the whole page.

The B-Tree invariant

✓ Cleared

A B-Tree node is a page. Instead of one key and two children, a node packs hundreds of sorted keys and as many children as keys plus one. The number of children a node can have is its fan-out, and fan-out is the whole trick: with a fan-out of 500, three levels reach 125 million keys.

The invariant that keeps this honest: every node except the root stays at least half full, and all leaves sit at the same depth. Inserting into a full node splits it in two and promotes the middle key upward; the tree grows from the root, never from the leaves, which is why it can never become unbalanced.

Searching and inserting

Reading now

A search is a walk from the root: binary-search the keys inside the node, follow the child pointer between the two keys that bracket your target, repeat. Each step is one page read, so the cost of any lookup is the height of the tree — three or four pages for tables of practically any size.

Insertion does the same walk to find the right leaf, places the key, and only does extra work in the rare case the leaf is full. The split promotes one key to the parent, which may itself split — a chain that reaches the root only once in millions of insertions.

B+ trees and range scans

Not yet

Real databases almost always use the B+ variant: interior nodes hold only routing keys, and every value lives in the leaves, which are chained left-to-right. A range query becomes one descent followed by a linked-list walk — no re-entering the tree between neighbours.

Indexes in practice

Not yet

An index accelerates exactly the queries whose predicates match its key order, and taxes every write. Choosing indexes is a workload decision, not a schema decision — which is why it is the last chapter of this Lesson and the first question of the next one.
